## 1. Ground-Truth Principles

1. **Human Verification Authority:** Ground truth is established by human cryptographic engineering inspection of known source fixtures. It is **NEVER** generated by running an external scanner or by querying an AI language model.
2. **Separation of Observed Fact from Expected Interpretation:**
   * **Observed Fact:** The literal syntactic construct in the file (e.g. line 16: `KeyPairGenerator.getInstance("RSA")`).
   * **Expected Interpretation:** The canonical domain classification that a sound scanner should derive (e.g. `algorithm: RSA`, `primitive: asymmetric_key_pair`, `role: unknown`).
3. **Strict Non-Inference of Operational Role:** If a source fixture instantiates a general key pair generator without an associated cipher or signature call site, the ground truth operational role **MUST** be recorded as `unknown`. Ground truth never forces or guesses a role.
4. **Preservation of Uncertainty in Ambiguous Cases:** For dynamic invocations (e.g. `Cipher.getInstance(envVar)`), ground truth explicitly requires `algorithm: UNKNOWN` and `confidence: NEEDS_REVIEW`. A scanner that claims a specific algorithm name here fails ground-truth verification.

    {
      "finding_id": "TC01-F01",

## 3. Human Verification Procedure

To verify an answer key:
1. Open the corresponding source code fixture in `product/benchmark/corpus/seed/<tc_id>/`.
2. Verify that line numbers in `observed_fact` match the actual source line coordinates.
3. Confirm that `raw_statement` matches the exact JCA/Python invocation.
4. Verify that `expected_interpretation.role` is justified solely by the code in the fixture without external assumptions.
5. In negative cases (`TC-10`), verify that `expected_findings` is empty, indicating that any finding detected is counted as a **False Positive**.
