# ECDAT Judge & Technical Defense Matrix

**Document Version:** 1.1.0 (Phase 0 Correction Pass)  
**Phase:** Phase 0 (Foundation & Constitution)  
**Objective:** Grounded, demonstrative defenses for SIH technical evaluations and viva defense.  

---

## 1. Defense Methodology

ECDAT does not rely on hand-waving or unsubstantiated claims. Every technical challenge posed by evaluators or enterprise security architects must be answered with **concrete architectural mechanisms, live workflows, verifiable evidence, and honest disclosures of limitations.**

---

## 2. Comprehensive Defense Matrix

| # | Evaluator / Judge Question | What ECDAT Demonstrates | Verifiable Evidence Required | Live Demo Path | Current Known Limitation |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Q1** | **"Why build ECDAT when tools like IBM CBOMkit, CryptoScan, and pqaudit already exist?"** | ECDAT is not a single scanner; it is a **scanner-agnostic intelligence platform** that combines discovery engines, normalizes to CycloneDX 1.7, computes multi-factor deterministic risk, prioritizes role-aware PQC migration, and verifies cryptographic retirement. | Pluggable adapter interfaces, CycloneDX 1.7 CBOM export, deterministic risk rule trees, and diffing engine. | Show adapter harness running multiple engines; show normalized CBOM and risk breakdown that external raw scanners do not produce. | Evaluated external scanners are currently candidates in Phase 0; benchmark validation occurs in Phase 1. |
| **Q2** | **"Why not simply use IBM CBOMkit directly?"** | CBOMkit is an extraction tool for CBOM generation. It lacks native contextual operational role modeling, enterprise PQC migration prioritization matrices, and commit-over-commit re-scan diffing. ECDAT can ingest CBOMkit output via an adapter while adding enterprise decision support. | CBOMkit adapter specification + ECDAT contextual risk engine comparison. | Ingest raw CBOMkit JSON into ECDAT adapter $\rightarrow$ generate prioritized PQC migration roadmap with risk scores. | CBOMkit adapter will be implemented and benchmarked in Phase 1. |
| **Q3** | **"Why not simply use CryptoScan?"** | CryptoScan provides static pattern detection for specific languages, but lacks standardized CycloneDX 1.7 CBOM compliance, enterprise deployment multi-tenancy, and cryptographic retirement verification across releases. | Scanner-agnostic adapter layer showing CryptoScan integrated alongside other engines. | Execute scan using CryptoScan adapter; demonstrate normalized output mapped into unified CBOM. | CryptoScan rules vary by language maturity; adapter isolation is required. |
| **Q4** | **"Why should an enterprise trust ECDAT with its proprietary repositories?"** | ECDAT supports 4 deployment modes. In Local CLI and CI/CD Agent modes, the system is **REQUIRED to ensure source code never leaves the organization's network**. Only sanitized metadata and CBOMs are generated. In Upload mode, scratch data is strictly ephemeral and REQUIRED to be purged post-scan. | Zero-network local CLI scan capability; network isolation tests; automated ephemeral directory purging tests. | Run local CLI scan with network interface disabled (`Disconnect-NetAdapter`); demonstrate full local CBOM generation with zero external traffic. | Enterprise on-prem multi-tenant RBAC and formal network test harness are planned for Phase 8. |
| **Q5** | **"Why should I upload my source code to your platform?"** | You do not have to. Upload mode is only for rapid demo or evaluation. Enterprise customers deploy the local CLI or agent within their own VPC, air-gap, or pipeline where source code remains strictly local by architectural requirement. | Local runner architecture, zero telemetry phone-home verification. | Execute `ecdat scan ./local-repo --local-only` showing immediate local JSON/CBOM output. | Upload mode requires container sandboxing (Phase 8). |
| **Q6** | **"What if your discovery scanner produces a false positive or misses something?"** | ECDAT uses an **evidence-first confidence model** (`CONFIRMED`, `LIKELY`, `POSSIBLE`, `NEEDS_REVIEW`). Analysts can triage findings with non-destructive review states while preserving original evidence provenance. | Evidence view showing file, line, code snippet, scanner ID, confidence score, and human review audit trail. | Open finding $\rightarrow$ inspect code snippet and AST confidence $\rightarrow$ mark as `FALSE_POSITIVE` $\rightarrow$ inspect audit log showing original evidence intact. | Dynamic reflection and obfuscated binary crypto cannot be confirmed via static analysis alone. |
| **Q7** | **"Can ECDAT detect every piece of cryptography in an enterprise?"** | **No, and we explicitly do not claim it can.** Static analysis cannot reliably detect heavily obfuscated code, runtime reflection, or encrypted binary blobs. ECDAT explicitly reports its **coverage boundary** and flags dynamic patterns as `NEEDS_REVIEW` rather than claiming zero crypto exists. | Documented coverage boundaries in `KNOWN_LIMITATIONS.md` and confidence scoring tags. | Scan a repo containing dynamic `Class.forName()` cipher calls; show that ECDAT reports `NEEDS_REVIEW` rather than false negative. | Deep binary reverse-engineering is out of scope for the static discovery engine. |
| **Q8** | **"Does AI make the authoritative security or risk decisions?"** | **Absolutely not.** Risk scores are 100% deterministic, calculated from transparent rule sets (algorithm, key length, quantum vulnerability class, operational context). AI is strictly an auxiliary explainer for human analysts and has zero authority to set or alter scores. | Deterministic risk formula documentation and air-gapped test execution with AI disabled. | Run risk calculation with AI turned off; show identical risk score and mathematical explanation breakdown. | AI summarization feature is slated for Phase 7 as strictly read-only advisory. |
| **Q9** | **"How is quantum risk calculated?"** | By evaluating algorithm vulnerability against Shor's algorithm (breaks RSA, ECC, DH) and Grover's algorithm (reduces symmetric search space, with AES-256 considered generally resilient subject to security model and implementation), combined with Mosca planning heuristics ($X+Y>Z$). | Quantum vulnerability classification matrix; NIST SP 800-131A & IR 8547 alignment; Mosca planning parameter documentation. | Show finding details: RSA-2048 flagged as "Critical Quantum Vulnerability (Shor's Algorithm)" with explanation of HNDL threat and shelf-life planning. | ECDAT does not claim to predict the exact date a CRQC will exist; threat horizon is an enterprise planning assumption. |
| **Q10** | **"How does ECDAT prioritize PQC migration?"** | Prioritization is strictly **role-aware**: (1) Key establishment $\rightarrow$ ML-KEM / hybrid schemes; (2) Digital signatures $\rightarrow$ ML-DSA / SLH-DSA; (3) Bulk encryption $\rightarrow$ symmetric review; (4) Exposure and data confidentiality lifetime ($X$). Universal replacement is rejected. | Role-aware migration matrix with NIST FIPS 203/204/205 mapping. | Display migration view showing high-exposure RSA key transport prioritized for ML-KEM-768, and RSA signatures prioritized for ML-DSA-65. | Automated dependency impact analysis is planned for Phase 6. |
| **Q11** | **"How do you verify that a cryptographic migration actually worked?"** | ECDAT's Re-scan Diff Engine compares Scan $N$ against Scan $N+1$ across Git commits, empirically verifying that legacy algorithms are retired, replacements are detected, and no regressive algorithms are introduced. | Historical scan diff reports showing $\Delta$ between commits. | Trigger Scan 1 (RSA present) $\rightarrow$ change code to ML-KEM / ML-DSA $\rightarrow$ trigger Scan 2 $\rightarrow$ show verification diff: "RSA Key Transport: RETIRED, ML-KEM-768: CONFIRMED". | Diff engine implementation is scheduled for Phase 9. |
| **Q12** | **"What happens if an external scanner is deprecated or removed?"** | The core ECDAT platform continues operating without disruption. The adapter for that scanner is simply deactivated in configuration; the domain model, risk engine, database, and UI require zero code modifications. | Pluggable `IScannerAdapter` registry and dependency decoupling. | Disable Scanner Adapter A; execute scan using Adapter B; verify core pipeline processes findings seamlessly. | Baseline adapter contracts specified in Phase 0; multi-adapter orchestration built in Phase 1. |
| **Q13** | **"What happens if an organization wants to add their own custom proprietary scanner?"** | They implement the standard `IScannerAdapter` interface (execute and normalize methods). Once registered, the custom scanner immediately feeds into the ECDAT normalization bus, risk engine, and CBOM exporter. | Open plugin adapter specification in `INTEGRATION_STRATEGY.md`. | Walk evaluator through implementing a 30-line custom regex adapter that integrates into the pipeline in minutes. | Plugin dynamic loading mechanism will be finalized in Phase 1. |
